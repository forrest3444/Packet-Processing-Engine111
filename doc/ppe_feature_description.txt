PPE 功能描述
版本：Draft 0.7
状态：基于当前已知规格整理；未确认内容统一标记为 [TBD]

1. 模块功能概述

PPE 模块接收来自多个输入 lane 的并行报文，将报文调度至内部 Forward Engine（FE）阵列进行处理，并将 FE 处理后的报文按照原始报文序严格输出。

FE 对报文处理后同时产生：
1) 处理后的报文；
2) 对应的内部处理结果。

处理后的报文通过输出 lane 对外输出。
内部处理结果不对外输出，仅用于满足后续报文的依赖处理。

2. Lane 组织

输入 lane 数与输出 lane 数相同，统一记为 N。

验证环境中的 N 可配置。
设计实现中的 N 当前固定为 4。
设计实现可保留参数化扩展能力，但当前设计和验证工作主要聚焦 N = 4。

FE 数量当前暂定与输入/输出 lane 数相同，即 FE_NUM = N = 4。

N 的完整支持范围：[4-8]

每个输入 lane 具有独立 valid。
不同输入 lane 可在同一周期独立提供报文。

输入 lane 编号仅表示物理输入位置，不表示报文先后顺序。
输入 lane 不要求按 lane 编号、周期顺序或 FE 调度顺序表达报文先后；PPE 只以 seq 建立全局顺序。

验证环境后期应具备可配置/可替换的抽屉化能力，支持不同 N 配置下与官方 golden RTL 进行回归比对。
当前阶段先以 N = 4 建立设计和验证主路径。

3. 输入接收与全局反压

PPE 通过全局反压信号 bkps 控制所有输入 lane。

bkps = 0：
PPE 允许接收输入。所有 valid 为 1 的输入 lane 上的报文均在本周期被接收。

bkps = 1：
PPE 禁止接收输入。所有输入 lane 同时被反压，本周期任何输入 lane 上的报文均不得被接收。

bkps 不支持 per-lane 独立反压。

bkps 拉高期间，上游必须保持 valid 和 data 稳定，直到 bkps 拉低且该报文被 PPE 接收。

4. 报文数据与报文序

每个输入报文的数据宽度为 128 bit。

每个报文携带能够确定其原始顺序的报文序信息。
报文序字段当前理解为包含在 128 bit 报文数据中。

报文序字段位于 128 bit 报文数据的低 32 bit，即 packet[31:0]。
报文序字段宽度为 32 bit。
报文序字段存在回绕，但当前设计阶段可暂按无限递增序号处理。
当前假设合法输入报文序连续均匀递增，不产生 seq 缺口、重复 seq 或非法乱序窗口。
同周期不同 lane 上的 seq 可以不按 lane 编号排列，但被 PPE 接收的全局报文序集合应保持连续合法。

PPE 必须根据报文序建立全局原始报文顺序。
报文顺序不得由输入 lane 编号、FE 编号、FE 完成顺序或输出 lane 编号推断。

5. 描述符

每个报文携带一个 5 bit 描述符。

descriptor[1:0]：
表示报文进入 FE 前由 PPE 人为插入的随路延迟周期数。
该延迟不表示系统端到端总延迟约束，也不要求 FE 处理延迟等于该值。

descriptor[4:2]：
相对依赖偏移 dep_offset。

描述符为独立接口字段，不包含在 128 bit 报文数据中。

描述符不需要传入 FE。
随路延迟、seq 报文序等控制信息由 PPE 外部逻辑或 PPE 内部调度逻辑维护，不作为 FE 输入报文字段处理。

6. 相对依赖语义

dep_offset = 0：
当前报文无依赖。

dep_offset = K，K 属于 1 至 7：
当前报文依赖其原始报文序之前第 K 个报文的 FE 处理结果。

若当前报文序为 S，则其依赖对象为原始报文序中的 S-K 对应报文。

依赖关系仅由全局原始报文序和 dep_offset 决定，与输入 lane、FE 编号和输出 lane 无关。

最大依赖查找深度为 7。

当被依赖报文的处理结果尚未由 FE 有效产生时，当前报文不得进入 FE。

若当前报文存在依赖，则 PPE 在送入 FE 前先将当前报文与对应依赖结果进行异或。
为保持 seq 报文序信息不变，当前设计建议仅对 packet[127:32] 与 dependency_result[127:32] 异或，packet[31:0] seq 保持原值。
异或后的报文作为 FE 输入报文。

无依赖报文送入 FE 时，直接将当前 128 bit 报文作为 FE 输入报文。

7. 依赖结果使用与生命周期

FE 产生的内部处理结果由 PPE 缓存，并按其对应报文序进行管理。

当前暂定语义：
1) 处理结果支持在合法窗口内被多个后续报文重复引用；
2) 依赖读取为非破坏性读取，读取结果不会清除 valid，也不会消耗该结果；
3) 处理结果缓存窗口覆盖当前报文之前最多 7 个报文；
4) 处理结果生命周期由报文序窗口自然推进决定；
5) 当某个结果对应报文已经离开后续报文可依赖的 7 报文窗口时，该结果可被后续结果覆盖；
6) 若结果仍处于合法查找范围内，覆盖或失效不得导致合法依赖丢失或永久等待。

处理结果缓存当前按前 7 个报文窗口进行管理。
无论结果是否被引用、是否被重复引用，其淘汰均由窗口推进决定，而不是由读取次数决定。
读取结果的建议定义为：依赖报文在进入 FE 前，从 Result Window 中读取 seq = S - dep_offset 对应的结果，并按上述规则与当前报文异或，同时保持 packet[31:0] seq 不变。

该语义等价于固定窗口上下文内的非破坏性 result cache。
对于当前报文 S，只有 S-1 至 S-7 的结果可能被引用。
当某个历史报文 R 与所有后续未处理报文的相对距离都已经大于 7 时，后续报文的 dep_offset 已不可能再指向 R，因此 R 的结果可以自然老化并被淘汰。
该自然老化语义依赖合法输入 seq 连续均匀递增；若激励产生 seq 缺口、重复或超出假设的非法乱序，则 7 报文窗口与实际依赖关系可能不再一致。

8. FE 阵列

PPE 内部例化多个 FE，形成 FE 阵列。

FE 是黑盒报文处理单元。赛题官方预计提供 FE 黑盒供系统例化，其内部处理算法不属于 PPE 规格范围。

在官方 FE 不可用时，设计中应提供一个可替换的 FE mock/stub，用于仿真、联调和 debug。
该 mock FE 不需要具备真实业务意义，但应具备可观测、可预测的处理逻辑，便于验证 PPE 控制路径。

PPE 负责：
1) 判断报文依赖是否满足；
2) 选择可用 FE；
3) 向 FE 提供当前报文及可选依赖结果；
4) 接收 FE 返回的处理后报文和内部处理结果；
5) 将返回结果与正确的原始报文序关联。

FE 数量：当前暂定为 4，与输入/输出 lane 数一致。
FE 输入接口：128 bit 报文。
FE 输出接口：128 bit 处理后报文，以及当前报文对应的内部处理结果。
FE 握手协议：当前建议采用标准 valid/ready 握手。
FE 输入侧信号建议为 fe_in_valid、fe_in_ready、fe_in_packet[127:0]。
FE 输出侧信号建议为 fe_out_valid、fe_out_ready、fe_out_packet[127:0]、fe_out_result[RESULT_W-1:0]。
FE 一次只处理一个报文，不支持同一 FE 内多个 inflight 请求。
FE 在空闲时可通过 fe_in_ready 接收新报文；接收后进入 busy，直到该报文处理完成并被输出侧握手接收。
FE 处理结果宽度：官方规格未明确。由于依赖使用方式为与 128 bit 报文异或，当前建议先按 128 bit 处理结果建模。

FE mock/stub 建议：
1) 参数化内部处理延迟，或根据输入报文低位生成 1 至若干周期的可变延迟；
2) 输出报文采用简单、可预测、便于 debug 的变换，例如 fe_out_packet = {fe_in_packet[126:0], fe_in_packet[127]} ^ 128'h固定常量；
3) 内部处理结果采用 128 bit，例如 fe_out_result = fe_in_packet ^ 128'h另一固定常量；
4) 保持输入报文低 32 bit seq 不变，便于外部观察保序输出；
5) mock 只用于验证 PPE 调度和依赖控制，不代表官方 FE 真实算法。

9. FE 处理延迟

FE 处理延迟不应被视为固定周期延迟。

不同报文的实际 FE 完成时间可能不同。
后进入 FE 的报文可能先完成。
PPE 必须依据 FE 的实际有效返回判断报文和处理结果是否完成。

PPE 的功能正确性不得依赖固定 FE 延迟，也不得假设不同 FE 之间按输入顺序返回。

FE 内部延迟范围：官方规格未明确。mock FE 可使用参数化或伪随机/数据相关延迟进行验证。

descriptor[1:0] 不控制 FE 内部延迟。
descriptor[1:0] 表示进入 FE 前由 PPE 插入的随路延迟周期数。

10. FE 返回数据管理

FE 返回的数据至少包括：
1) 处理后的报文；
2) 当前报文对应的内部处理结果。

PPE 必须将处理后的报文和内部处理结果与正确的原始报文序绑定。

处理后的报文用于最终输出。
内部处理结果仅用于后续依赖处理，不得出现在外部输出中。

FE 返回接口本身不携带报文序、descriptor 或其他控制信息。

PPE 仍必须在 FE wrapper 或调度表中保存每个已派发请求的内部关联标识。
这里的“tag”不是 FE 业务控制信息，也不是需要传入 FE 的报文字段，而是 PPE 内部用于将 FE 返回数据匹配回正确 ROB entry 的 bookkeeping 信息。
由于每个 FE 同一时间只允许一个 inflight 请求，PPE 可在每个 FE wrapper 中保存该 FE 当前正在处理的 ROB index。
FE 返回有效并完成输出握手时，PPE 使用该 FE 保存的 ROB index 写回正确 ROB entry。

11. 严格保序输出

PPE 最终输出必须严格保持原始报文序。

若原始报文顺序为 A、B、C，则最终输出顺序必须为 A、B、C。

即使 B 或 C 先于 A 完成 FE 处理，B 和 C 也不得越过 A 输出。

每个被 PPE 成功接收的合法报文必须：
1) 被 FE 处理一次；
2) 最终输出一次；
3) 不丢失；
4) 不重复；
5) 不与其他报文错配；
6) 不破坏原始报文序。

当前标准方案下，PPE 不主动丢弃已接收报文。
若出现异常或非法依赖，建议内部进入 stall 状态或触发仿真断言，而不是静默丢包或错序输出。
当前外部接口不包含 error_valid/error_code 等错误码相关端口。

12. 输出 lane 循环分配

输出接口无 ready，仅具有每个 lane 独立的 valid 和输出数据。

输出 lane 按固定循环顺序使用：

lane0 -> lane1 -> ... -> lane(N-1) -> lane0 -> ...

PPE 维护当前输出起始 lane。

输出起始 lane 不在每个周期重置。
空闲周期不得推进或重置输出起始 lane。
输出起始 lane 仅根据实际输出的报文数量推进。

当同一周期输出多个连续报文时，报文按照当前输出起始 lane 开始，依次映射到后续 lane；到达 lane 上限后从 lane0 继续。

示例：
N = 4，当前输出起始 lane 为 lane1，待输出报文依次为 A、B、C。
本周期输出映射必须为：
lane1 -> A
lane2 -> B
lane3 -> C

下一输出起始 lane 为 lane0。

输出循环分配必须在保持严格报文序的前提下实现各输出 lane 的负载均衡。

复位后初始输出起始 lane：lane0。

13. 复位行为

复位后，PPE 应清除或重新初始化以下状态：
1) 已接收但未处理的报文状态；
2) FE 调度状态；
3) 已完成但未输出的报文状态；
4) 内部依赖结果及其有效状态；
5) 输出 lane 循环状态；
6) 全局反压相关状态。

复位建议采用低有效同步复位 rst_n。
复位期间 PPE 清空内部状态，忽略 FE 返回数据，并将 FE wrapper 中的 busy/tag 状态清空。
复位后首次输出 lane：lane0。

14. 异常与非法依赖场景

在输入报文满足赛题约束时，系统应避免进入异常依赖状态。
但为了实现和验证，应明确以下异常场景：

1) 依赖对象尚未被 PPE 接收。
例如当前报文 seq = S、dep_offset = 3，但 S-3 对应报文尚未到达。
当前按合法输入 seq 连续均匀递增处理，该场景不应由正常激励产生。
若后期验证需要支持更宽松的输入乱序，此时当前报文应等待；但这会增加 ROB 和窗口管理复杂度。

2) 依赖对象已接收但尚未完成 FE。
这是正常等待状态，不属于错误。当前报文必须停留在 WAIT_DEP，直到依赖结果 valid。

3) 依赖结果在合法窗口内被多个后续报文重复引用。
这是合法场景。Result Window 读取为非破坏性读取，同一个结果在离开缓存窗口前可以被多个距离不超过 7 的后续报文引用。

4) 依赖结果已滑出 7 报文窗口或被 FIFO 覆盖。
例如报文 S 依赖 S-K，但目标结果已经不在前 7 个报文缓存窗口中。
在 dep_offset 仅为 1 至 7 且系统正确阻止提前覆盖合法窗口结果时，该场景不应发生；若发生，说明输入描述符非法、结果管理错误或窗口推进策略错误。

5) seq 重复、跳号或回绕处理不一致。
当前阶段暂按无限递增处理，因此重复 seq 或明显跳号可能导致 ROB 查找和输出指针异常。
当前激励应避免产生此类非法包。标准实现可在 debug/仿真中检测该类情况，正式数据路径先以赛题输入合法为前提。

建议异常处理策略：
1) 仿真/调试版本可通过内部 debug 信号或断言定位非法依赖、重复 seq、窗口丢失等问题，不作为正式外部接口；
2) 综合主路径不主动丢包，不输出错误报文；
3) 发生不可恢复异常时保持阻塞状态，并依赖 reset 恢复；
4) 若赛题明确保证输入合法，可将异常检测作为断言或 debug-only 逻辑。

15. 核心功能不变量

1) 输入 lane 编号不决定报文序。
2) dep_offset 仅表示相对于原始报文序的依赖距离。
3) dep_offset = 0 表示无依赖。
4) 最大依赖查找深度为 7。
5) 依赖结果未产生时，依赖报文不得进入 FE。
6) 依赖结果必须与正确的历史报文匹配。
7) 依赖结果在合法 7 报文窗口内支持重复引用，读取为非破坏性读取。
8) FE 可乱序完成，但最终输出必须严格保序。
9) 内部处理结果不得出现在外部输出中。
10) bkps 拉高时所有输入 lane 同时停止接收。
11) 输出 lane 按持续循环方式分配。
12) 空闲周期不得改变输出循环状态。
13) 每个合法接收报文最终只能输出一次。
14) descriptor[1:0] 表示进入 FE 前的人为随路延迟，不约束 FE 内部处理延迟。
15) descriptor 不进入 FE。
16) 有依赖报文进入 FE 前，应先与对应依赖结果异或，并保持 packet[31:0] seq 不变。
17) bkps 拉高期间，上游必须保持 valid/data 稳定。
18) 单个 FE 不支持多 inflight；PPE 可按 FE 编号保存当前 ROB index。
19) PPE 不主动丢弃已接收报文，异常状态应通过内部 debug 或断言暴露，正式接口不携带错误码。
20) 合法输入 seq 按全局报文序连续均匀递增；激励不得产生 seq 缺口或重复 seq。

16. 建议实现架构

建议 PPE 内部采用 ROB（Reorder Buffer）作为主状态结构。
ROB 用于统一管理已接收但尚未输出的报文，并支持 FE 乱序完成后的严格保序输出。

每个 ROB entry 建议至少包含：
1) entry valid；
2) 32 bit seq；
3) 128 bit 原始报文；
4) 5 bit descriptor；
5) dep_offset；
6) 当前状态，例如 WAIT_DELAY、WAIT_DEP、READY_FE、IN_FE、DONE；
7) 随路延迟剩余计数；
8) 处理后报文；
9) 内部处理结果；
10) 结果 valid 状态。

推荐处理流程：
1) Input Collector 在 bkps = 0 时接收所有 valid lane 报文，解析 seq 和 descriptor，并写入 ROB。
2) Delay/Dependency Manager 先处理 descriptor[1:0] 指定的进入 FE 前随路延迟，再检查 dep_offset 对应依赖结果是否有效。
3) FE Scheduler 从 READY_FE 报文中选择请求，必要时先执行 packet XOR dependency_result，再派发给空闲 FE。
4) FE wrapper 保存 PPE 内部关联标识，接收 FE 返回后写回正确 ROB entry。
5) Output Reorder 从 next_output_seq 开始选择连续 DONE entry，最多每周期输出 N 个，并按持续循环 lane 指针分配输出 lane。
6) Result Window 保存最近最多 7 个可被依赖的内部处理结果，结果按窗口推进规则自然老化并失效。

bkps 建议由 ROB 空间、结果窗口安全性以及 FE 返回接收能力共同决定。
当下一周期可能无法完整接收所有输入 lane 的合法 valid 报文时，应拉高全局 bkps。
