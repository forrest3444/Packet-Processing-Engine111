第一部分：我的分析 vs 原规格文档 — 一致点确认
--------------------------------------------------------------------------------
以下是我在未阅读原规格文档情况下，从 RTL 代码中正确推断出的设计要点：

  ✓ ROB 架构、6 状态机 (ST_EMPTY/WAIT_DELAY/WAIT_DEP/READY_FE/IN_FE/DONE)
  ✓ 全局反压 bkps 语义（所有 lane 同时阻塞）
  ✓ desc[1:0] = 进入 FE 前的随路延迟；desc[4:2] = dep_offset (1-7, 0=无依赖)
  ✓ 依赖目标 seq = 当前 seq - dep_offset
  ✓ 有依赖报文需先与 dependency_result 异或后再送入 FE
  ✓ packet[31:0] (seq) 保持不变，仅 packet[127:32] 参与异或
  ✓ 严格保序输出（按 seq 顺序 commit）
  ✓ 输出 lane 轮转分配 (round-robin, out_start_lane)
  ✓ FE Mock 实现与规格建议一致（参数化延迟、XOR 变换、保持 seq 不变）
  ✓ Single inflight per FE，通过 fe_busy/fe_rob_idx 做 bookkeeping
  ✓ 输出接口无 ready，仅 valid + data

================================================================================
第二部分：关键差异 (RTL vs 规格) — 高风险项
================================================================================

--------------------------------------------------------------------------------
CRITICAL-1: Result Window 完全缺失
--------------------------------------------------------------------------------
规格要求：
  第 7 节明确要求 PPE 维护一个 "Result Window"，仅缓存最近 7 个报文的结果。
  结果应按窗口推进自然老化淘汰。最大依赖查找深度为 7。
  第 15 节明确 "最大依赖查找深度为 7"。

RTL 实际：
  - 结果存储在 res_valid[0:ROB_DEPTH-1] / res_data[0:ROB_DEPTH-1] 中
  - 索引方式为 ROB entry index，不是按 seq 窗口管理
  - 结果 valid 置 1 后 NEVER CLEARED（即使在 ROB entry 被释放后）
  - 依赖搜索遍历全部 ROB_DEPTH(32) 个条目，而非 7 条目窗口
  - 完全没有结果老化、淘汰逻辑

风险等级：★★★★★ (最高)
影响：
  1) 依赖查找窗口实际为 32 而非 7，与规格不一致
  2) 无老化机制，陈旧结果永久残留
  3) ROB entry 释放时 res_valid 不清零 → 陈旧结果可能被后续依赖误匹配
     （虽通过 seq 匹配有一定保护，但设计不严谨）
  4) 规格要求的 "窗口推进自然淘汰" 语义完全未实现

--------------------------------------------------------------------------------
CRITICAL-2: ERR_BAD_DEP 定义但从未使用
--------------------------------------------------------------------------------
规格要求：
  第 14 节建议异常检测暴露 error_valid/error_code，用于定位非法依赖

RTL 实际：
  - ERR_BAD_DEP (8'h02) 定义为 localparam，但在整个 ppe_core.v 中
    从未被赋值给 error_code
  - 当依赖永远无法满足时（如 dep_offset 指向不存在的 seq），ROB entry
    永久卡在 ST_WAIT_DEP，无任何错误上报

风险等级：★★★★★ (最高)
影响：未实现规格中要求的异常可观测性

--------------------------------------------------------------------------------
CRITICAL-3: 无死锁检测 / 超时机制
--------------------------------------------------------------------------------
规格要求：
  第 11 节："若出现异常或非法依赖，建议进入可观测的 error/stall 状态，
  而不是静默丢包或错序输出"
  第 14 节：异常时应保持阻塞状态并依赖 reset 恢复

RTL 实际：
  - ST_WAIT_DEP 状态：无限等待依赖，无超时 / watchdog
  - ST_IN_FE 状态：无限等待 FE 返回，无超时
  - 以上任一情况发生，ROB entry 永久占用，最终耗尽 ROB 导致系统死锁
  - 死锁后无任何 error_flag 上报

风险等级：★★★★★ (最高)
影响：单点故障 → 全局死锁，无恢复路径（仅靠 reset）

--------------------------------------------------------------------------------
CRITICAL-4: ROB Index = seq[4:0] 的别名冲突风险
--------------------------------------------------------------------------------
规格要求：
  未规定 ROB 索引方式。但 seq 为 32 bit，报文序连续递增。

RTL 实际：
  - rob_idx = seq_tmp[ROB_AW-1:0]，即用 seq 的低 5 bit 直接做 ROB index
  - seq=1 和 seq=33 映射到同一个 ROB slot
  - ERR_DUP_SEQ 检测同一 ROB index 是否 active，但存在 bug（见 CRITICAL-5）

风险等级：★★★★
影响：
  1) 有效 ROB 深度受限于 seq 低位分布，而非真正的 32 条目
  2) 虽然 seq 连续递增时自然形成循环使用，但任何异常都会暴露问题
  3) 若 seq 回绕（32 bit），低 5 bit 的循环与全局 seq 顺序可能不一致

--------------------------------------------------------------------------------
CRITICAL-5: error_valid 已置高时重复 seq 被静默覆盖
--------------------------------------------------------------------------------
RTL 代码 (ppe_core.v:308-326)：
  if (rob_active[rob_idx] && !error_valid) begin
      error_valid <= 1'b1;       // 仅在 !error_valid 时上报
      error_code  <= ERR_DUP_SEQ;
  end else begin
      // 当 error_valid 已为高时，走 else 分支 → 静默覆盖 ROB entry！
      rob_active[rob_idx] <= 1'b1;
      ...
  end

风险等级：★★★★
影响：首个错误发生后的同周期/下一周期重复 seq 会静默覆盖活跃 ROB entry，
      导致数据损坏、丢包、状态不一致。

--------------------------------------------------------------------------------
HIGH-6: bkps 为组合逻辑输出
--------------------------------------------------------------------------------
规格要求：bkps 为全局反压信号

RTL 实际：
  always @(*) begin
      ...
      bkps = error_valid || (free_count < input_count);
  end

风险等级：★★★
影响：
  1) 组合逻辑输出 → 下游采样可能捕获毛刺
  2) free_count 和 input_count 也在同一组合块中计算，时序路径可能较长
  3) 建议打一拍寄存器输出

--------------------------------------------------------------------------------
HIGH-7: started 标志与 next_output_seq 初始化假设
--------------------------------------------------------------------------------
RTL 代码 (ppe_core.v:297-300)：
  if ((!started) && min_found) begin
      started         <= 1'b1;
      next_output_seq <= min_seq;  // 首拍的 min_seq 作为输出基线
  end

风险等级：★★★
影响：
  1) started 一旦置 1 永不清零（仅 reset）
  2) next_output_seq 初始化为首批输入中最小 seq。若首批不包含全局最小 seq
     （如 reset 后首拍只有 seq=5/8/12），则 0-4 理论上永远无法被 commit
  3) 规格假设 seq 连续均匀递增从某个值开始，但未明确首拍必须包含最小值

--------------------------------------------------------------------------------
HIGH-8: 依赖查找无 desc[4:2] 范围校验
--------------------------------------------------------------------------------
RTL 使用 desc[4:2] 直接做减法 rob_seq - desc[4:2]。若 desc[4:2] 超出合法
范围（如大于当前 seq），减法结果无意义，搜索 res_seq 将找不到匹配 → 永久
ST_WAIT_DEP。

风险等级：★★★
影响：非法 descriptor 输入可导致死锁

--------------------------------------------------------------------------------
MEDIUM-9: FE Mock ready 信号竞争窗口
--------------------------------------------------------------------------------
fe_mock.v 中 fe_in_ready = (!busy) && (!fe_out_valid)。
在 delay_cnt 归零的同一周期：busy 清零 + fe_out_valid 置 1。
此时 fe_in_ready 也变 1。存在极窄窗口：消费者同时看到 fe_out_valid=1 和
fe_in_ready=1。虽然 ppe_core 的 fe_out_ready 恒为 1 会快速消费，但设计上
存在隐患。

风险等级：★★
影响：极端 corner case 下可能导致协议违规

--------------------------------------------------------------------------------
MEDIUM-10: 组合调度逻辑的时序收敛风险
--------------------------------------------------------------------------------
组合 always 块包含三重嵌套循环（Lane × ROB × ROB），在 ROB_DEPTH=32、
LANE_NUM=8 时可能产生严重时序路径。

风险等级：★★
影响：高频设计可能需要流水化

第三部分：规格中有但 RTL 未实现的功能
================================================================================

  1. Result Window (7-entry, aging, eviction)      → 未实现
  2. ERR_BAD_DEP 异常检测                           → 定义但未使用
  3. seq 跳号/缺口检测                              → 未实现
  4. 依赖窗口合法性校验                             → 未实现
  5. FE 超时检测                                    → 未实现
  6. 任何形式的性能计数器/调试可观测性              → 未实现
  7. 结果缓存窗口的自然老化与淘汰                   → 未实现
